RA · semantic What diverged

Side-by-side relational algebra shows the intent is usually close. Three recurring gaps:

  • Over-projection · missing outer π. idx 4 gold projects only year; pred also returns the SUBSTR(Date) key and the SUM value — extra columns. (drives SELECT #1)
  • Wrong γ granularity / derived value. idx 5 gold groups by month and filters year='2013'; pred groups by full Date and uses a BETWEEN string range.
  • Equivalent-but-different aggregation. idx 9 gold uses one pass of SUM(IIF(...)); pred subtracts two COUNT(*) subqueries — logically equal, but it mis-cased 'discount' vs 'Discount' and the result set breaks.
BNF · grammar How it errs

Top-level production sequences are nearly identical (SELECT…FROM…WHERE…GROUP BY…ORDER BY…LIMIT). The divergence is in the low-level expansions:

  • <proj> expands to extra terminals — superfluous AS <alias> and columns.
  • <cond> picks BETWEEN / ≥ ∧ ≤ where gold uses = on a derived value.
  • <agg> picks a COUNT(*) subquery composition over gold's SUM(IIF(...)).

i.e. the model chooses a grammatically valid expansion — just not gold's.

Root cause — the last mile, not the plan. The high-level SQL plan (BNF top level, RA main structure) is usually correct. Failures concentrate on: (1) BIRD gold's terse output convention — the model over-returns helper/aggregate columns (SELECT = 79%); (2) insensitivity to the schema's real values/formats — case, date encoding, casts (inflates WHERE / FUNCTION / CAST); (3) EX counting only gold's phrasing, so a valid equivalent query still fails on a small literal bug. Fix priority: hard-constrain the output columns in the prompt and inject real value samples for the target columns.
